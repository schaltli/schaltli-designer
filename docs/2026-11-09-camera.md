# Camera

Spec drafted 2026-11-09 from docs/ideas/kamera.md (its section «Update
2026-11-09»). **Status: approved by the user on 2026-11-09.**

## Objective

A new object type, **Camera**, shows the picture of a camera on a Schaltli
screen: a dog left in the van, a glance at something out of reach, the ground
under the van when stopping over a drain. It is for whoever builds a van's
screens and has a camera on the network with a snapshot URL.

Success: the user places one object, types in a URL, and sees a moving picture
on every touch device, with a delay that stays small and a dead camera that
cannot pass for a live one.

## Decisions

1. **The object only shows a picture** (the user, 2026-11-09). No power topic,
   no maximum time, no open or close actions, here or later on this type.
   Switching a camera, a relay or a lens cover is done with other blocks, which
   is more flexible. This overrides the idea's lifecycle and power topic.
2. **A type of its own**, `camera`, labelled «Camera». Same object in the
   designer for every device.
3. **Properties:** `url` (`http://` only), and optionally `username` and
   `password` for HTTP Basic (the user). No interval, no resolution setting.
4. **One image after another, only while visible.** A device requests the next
   image when the last has arrived. Off-screen, in a closed popup or with the
   display off it makes no request.
5. **Read to `Content-Length`**, not to the end of the connection; without that
   header, to the end. The spike went from 4-5 to about 11 fps with this alone.
   The connection is kept when the server allows it.
6. **The next image is fetched once the last is decoded** (the user, 2026-11-09,
   after HIL on the 4": fetching ahead fetched 19 images a second and showed 3.3).
   With single images nothing can queue, so waiting costs no freshness. No MJPEG:
   the spike showed 1-10 s of delay.
7. **One state besides the picture.** Whenever no image younger than 1 s is
   shown, including before the first, the object shows «No live image» instead
   of a picture. The same on every device.
8. **Size 80x60 to 320x240, default 320x240**, on every device: VGA missed the
   frame rate on the 4". The picture is fitted whole and centred; a larger
   source is scaled down while decoding (1/2, 1/4, 1/8), a smaller one is not
   enlarged. The handbook recommends a 320x240 source.
9. **Devices:** Waveshare 4", 4.3B, Knob, Android (the user). PaperS3 does not
   declare the type, so the designer does not offer it there.
10. **Credentials travel in the clear in the project and DDF**, as the user
    chose. The field is masked in the designer; they never appear in device
    logs, `/api/debug` or status messages. The handbook says so.
11. **HTTP only on devices.** HTTPS, Digest and RTSP go through go2rtc on the
    Pi, which gives a plain URL.
12. **Not for reversing or driving.** The handbook warns so, with one exception:
    positioning over a drain, at walking pace, after looking around.
13. **A device accepts images up to 256 KB** (the user); larger ones count as no
    image (success criterion 9).
14. **Powering a camera needs nothing from this feature** (the user). Today a
    switch on the screen toggles a relay. One tap that opens a popup and
    switches a relay, and switching off when the popup closes, is a feature of
    its own: several actions on a button and an OnClose on popups (the user,
    2026-11-09). A button has one action today, and popups have no such event.
    The Camera does not wait for it.

## Device contract (`camera-export`)

```json
{
  "type": "camera",
  "x": 80, "y": 40, "width": 320, "height": 240,
  "properties": {
    "url": "http://192.168.8.50/capture",
    "username": "",
    "password": ""
  }
}
```

A device supporting it adds `"camera"` to `supportedObjectTypes`.

## Designer (`camera-designer`)

Canvas: a neutral placeholder with a camera icon and the object's size. Preview:
the image from the URL where a browser can load it, otherwise the placeholder
(https pages block http images; `<img>` cannot send the credentials). The demo
instance shows a still image. Handbook: a new object page with setup for a XIAO
and a phone with IP Webcam, go2rtc, the credentials note and the warning of
decision 12.

## Tech

Firmware: JPEGDEC (a new dependency, bitbank2/JPEGDEC, used by the spike) with
its working memory in PSRAM, since internal RAM is short. Android: whatever the
app already uses for HTTP and bitmaps.

## Testing

- **e2e:** `e2e/camera.spec.ts`: place, set URL, masked password, preview with a
  mocked image and with a failing one, export contains the fields.
  `e2e/handbook-labels.spec.ts` covers the handbook's labels.
- **HIL:** a small camera server under `hil/` serving JPEGs of known colour at a
  chosen size, slow on demand, stopping on demand, with and without
  `Content-Length`, requiring Basic on demand. A Camera case in the fixtures of
  `hil/waveshare/`, `hil/waveshare4v3b/` and `hil/android/`. Knob likewise.
- `hil/conformance/specimens.js`: a Camera specimen for designer and device
  against each other.

## Success criteria

On the real firmware, with renderer and MQTT running, measured by HIL:

1. 4" and 4.3B show at least 5 images a second at 7-11 KB on the bench WiFi.
2. The delay does not grow: over 5 minutes with a slowed server, a shown image
   is never older than 1 s while the state is not «No live image».
3. «No live image» appears within 1.5 s of the server stopping, and the picture
   returns by itself within 3 s of it starting again.
4. The main loop pauses at most 150 ms longer than the same screen without a
   Camera; taps and live values still work. (100 ms flat was out of reach: an
   energy diagram alone gives 126 ms. It and a Camera on one screen are the worst
   case, not a likely one.)
5. Internal free RAM stays at least 20 KB above what the board needs without a
   Camera; no restart in a 30-minute run.
6. No request while the object is not visible.
7. Basic auth works; the password appears in no device log or debug output.
8. Knob: as 1, 3 and 4. If it misses them, the user decides before it declares
   the type.
9. A wrong URL, an image that is no JPEG and one over the size limit each lead to
   «No live image», never to a crash.

The first task of `camera-firmware` measures 1 and 4 with the renderer and MQTT
running; if they fail, the frame rate is capped before anything else is built.

## Boundaries

- Always: the handbook in the same piece of work; `npm run typecheck` before
  `test:quick`; every device behaving alike.
- Ask first: dropping a device from decision 9; a limit below decision 8; any new
  dependency beyond JPEGDEC.
- Never: credentials in logs; logic on this object (decision 1); MJPEG.
