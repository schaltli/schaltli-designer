# Undo and redo in the designer

Agreed 2026-09-23. Closes issue #5.

The designer has no undo. Deleting an object, a screen or a topic takes effect
at once, and the only nets are the server autosave (which keeps the mistake
too) and Version History (which only checkpoints on deploy). The handbook warns
about it twice under `handbuch-macke #5`. `keyboard-handlers.ts` already lists
`z` and `y` as known shortcut keys, but nothing is behind them.

## Objective

Someone editing a project can take back any change to it with Ctrl+Z (Cmd+Z
on the Mac) and bring it back with Ctrl+Y or Ctrl+Shift+Z, as they would in
any other editor, so that a slip costs one keystroke instead of a re-upload.

Decisions taken with the user on 2026-09-23:

1. **Everything in the project is undoable**: objects, screens, topics,
   project settings, fonts, assets, hardware-button actions, bausteine. What is
   not part of the `Project` value is not: zoom, pan, selection, active tool,
   preview mode, panel widths, the object clipboard.
2. **One step per gesture**, not per state update. A drag, a resize, a rotate
   or an arc-handle move is one step. Typing into a property field is one step
   per field edit (see *Step boundaries*).
3. **No delete confirmation.** Undo is the safety net; a dialog in front of
   every delete is not added. Issue #5 is closed by this work alone.
4. **Keys and toolbar buttons.** Two buttons, *Undo* and *Redo*, in the
   toolbar, disabled when there is nothing to undo or redo.

## Behaviour

### What a step is

A step is the `Project` value before a change together with the
`currentScreenId` and `selectedObjectIds` at that moment. Undo puts that
project back, switches to that screen and restores that selection, so the user
sees what was undone rather than having it happen on a screen they are not
looking at - and a deleted object comes back selected, ready to be moved or
deleted again. Undo pushes the state it leaves (project, screen, selection)
onto the redo stack, so redo restores the state right after the change the
same way. Restored ids that do not exist in the restored project are dropped,
as a guard, not as the expected case.

### Step boundaries

- A change made while a pointer gesture on the canvas is in progress (mouse
  down to mouse up) joins that gesture's step.
- A change made while a text, number or colour input has focus joins the
  previous step if it came from the same input and less than 1 s after the
  previous change. Blur, or a 1 s pause, closes the step.
- Every other change is its own step: a delete, a paste, a menu command, a
  dialog's OK, a drop from the toolbar.
- A change that leaves the project deep-equal to before (a click without a
  move) creates no step.

### What does not create a step

These replace the project wholesale and **clear** both stacks instead,
because undoing across them would mix two projects:

- loading or uploading a project,
- creating a new project,
- restoring an autosave or a Version History entry,
- choosing a device in the startup gate.

Normalisations the editor applies on its own (for example integer rounding on
load) are part of the load and create no step either. Any other `setProject`
that runs without a user action is found and listed during planning; each one
either becomes part of a load or is excluded from history, never a step the
user did not make.

### Keys

| Keys | Action |
|---|---|
| Ctrl+Z / Cmd+Z | Undo |
| Ctrl+Y / Cmd+Y | Redo |
| Ctrl+Shift+Z / Cmd+Shift+Z | Redo |

Like the existing Ctrl+C/V/A they do nothing in preview mode, and while an
input, textarea, select or contenteditable has focus they are left to the
browser, so undo inside a text field stays the field's own undo.

### Limits

- History holds the last **100** steps; the oldest is dropped beyond that.
  Steps share structure with each other (the project is updated immutably), so
  the cost is the changed branches, not 100 full copies.
- A new change after an undo discards the redo stack.
- History lives in memory only. A reload starts with empty history; the
  autosave still restores the project itself.
- Undo and redo change the project like any other edit, so autosave picks them
  up through its existing debounce.

## Tech stack

Next.js / React 19, TypeScript, state in `useState<Project>` in
`components/project-editor.tsx`, Playwright for tests. No new dependency: the
history is a small module of our own, not `use-undo`, `zundo` or Immer
patches.

## Approach (to be detailed in the plan)

- `lib/project-history.ts`: a pure history structure (`past`, `future`,
  record, undo, redo, clear, limit) with no React in it.
- A hook in `project-editor.tsx` that records the previous project whenever
  `project` changes, *unless* the change came from undo, redo or a load. It
  records after the fact (from the committed value), not inside the
  `setProject` updater, because updaters run twice under StrictMode.
- The canvas reports gesture start and end (it already tracks `dragState`
  and has one `handleMouseUp`), so the hook knows when a gesture's step closes.
- Undo/redo keys join the existing `handleKeyDown` in `project-editor.tsx`
  beside copy, paste and select all.

## Code style

As the rest of the repo: comments say *why*, with a date when they record a
decision, and name the file that holds the other half.

```ts
// Records after the commit, not inside setProject's updater: StrictMode
// runs updaters twice, which would push every step onto the stack twice
// (docs/2026-09-23-undo.md).
useEffect(() => {
  const previous = previousProjectRef.current
  previousProjectRef.current = project
  if (skipNextRecordRef.current) {
    skipNextRecordRef.current = false
    return
  }
  history.record(previous, currentScreenId, stepKey())
}, [project])
```

## Testing strategy

Playwright against the running app, as the rest of `e2e/`; no unit-test
framework is added. `e2e/undo.spec.ts` covers at least:

- move an object by drag → one Ctrl+Z puts it back exactly, Ctrl+Y moves it
  again,
- delete an object, a screen, a topic → Ctrl+Z restores each, including its
  id and position in the drawing order,
- type a new label into a property field → after blur, one Ctrl+Z restores the
  whole old label,
- Ctrl+Z while a text field has focus does not touch the project,
- undo switches to the screen the change was made on,
- undo of a delete reselects the restored objects; redo restores the
  selection as it was right after the change,
- a new edit after undo empties redo (Redo button disabled),
- loading another project clears history (Undo button disabled),
- 101 changes → the first can no longer be undone, the second can,
- Undo/Redo buttons do the same as the keys and are disabled when empty.

`e2e/handbook-labels.spec.ts` covers the new toolbar labels once the handbook
quotes them.

## Boundaries

- **Always:** keep undo, redo and clear in `lib/project-history.ts` and the one
  hook, never scattered across call sites; run `npm run typecheck` and the
  e2e suite before each commit; update the handbook in the same piece of work.
- **Ask first:** changing how an existing `setProject` call site behaves beyond
  what history needs; adding a dependency; persisting history across reloads;
  anything that changes what gets deployed or autosaved.
- **Never:** put selection, zoom or other view state into `Project` to make it
  undoable; touch `schaltli-firmware`, `schaltli-android` or `schaltli-eink`;
  skip or weaken an existing test to get green.

## Settled after the draft (2026-09-23)

1. Toolbar: icon buttons with the tooltips *Undo* and *Redo* plus the
   shortcut, English like the rest of the UI.
2. Undo and redo restore the selection with each step (see *What a step is*),
   not just drop stale ids.
3. A deploy binds the project to the device it went to
   (`settings.boundInstanceId`). That is a fact, not an edit: it is no undo
   step, and undo and redo always keep the current binding rather than
   restoring the one stored in a step. Only a new deploy, a load or a restore
   changes it.
