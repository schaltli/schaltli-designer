# Live data: the VanPi bridge, a live preview, and empty until real

Agreed 2026-09-15. The goal, in the user's words: someone who installs the
designer on their VanPi should be able to design their own screens and try
them straight away, against their own van.

## Where it starts

- **Pekaway's MQTT API answers, it does not announce.** `pkw/stat/<x>` is a
  request, `pkw/tele/<x>` its JSON answer; with "Send stats via MQTT"
  switched on, everything arrives only every five minutes. A panel or a
  preview that just subscribes sees nothing for minutes. Read off the running
  system (VanPi_Ctrl v2.0.10): `batt`, `level`, `temp`, `relay`, `dimmer`,
  `heater`, `bms`, `mppt`, `fan`, `maxxfan`, `info`; commands
  `pkw/cmnd/relay/<n>/POWER` and `wrelay` (`on`/`off`/`true`/`false`),
  `dimmer/<n>/POWER` (0-100, `on`/`off`), `heater/POWER`,
  `heater/POWER/<12-35>`, `switchall/POWER`, `maxxfan/#`.
- **The broker can expire messages.** Mosquitto 2.0.11 with persistence on.
  Tested on the van's broker: a retained message published with an MQTT 5
  message expiry of 5 s reached a 3.1.1 subscriber after 1 s and was gone
  after 8 s; one without expiry stayed. There is no broker-wide default -
  only a publisher speaking MQTT 5 can set it, and the panels' PubSubClient
  speaks 3.1.1.
- **The preview never touches a broker.** It shows each topic's first
  example, edited values from the Topic Values panel, and answers from the
  mock engine.
- **A device shows the first example until a real value arrives**
  (`ProjectLoader.cpp`: `currentValue = examples[0]`).

## Decisions

**1. The designer installs a Node-RED bridge on the VanPi.**
A tab of its own, "ScreenBee VanPi Bridge", added through Node-RED's admin
API - Pekaway's flow file is never edited by hand. It asks Pekaway's MQTT API
every two seconds, splits the JSON answers into single values, and publishes
the ones that changed; after a command it asks again at once, so a switch
does not wait for the next round. Only Pekaway's documented API is used, not
its internal variable names. Installed, updated and removable by the
designer's install script; a Pekaway update that replaces the flow file loses
it until the next designer update puts it back.

**2. Topics live under `screenbee/`.**
`screenbee/state/<group>/<n>/<value>` and `screenbee/cmnd/<group>/<n>`, in
English and lower case, so designs can be shared. `state` and `cmnd` become
reserved: no device client id may take either name, and no bridge topic has
three levels ending in a device leaf (`hello`, `status`, `deploy`,
`deploy-status`, `firmware`), which the designer subscribes to as
`screenbee/+/<leaf>`. No manufacturer name in the topics.

**3. State is retained, without expiry.**
A panel or a preview that connects gets the last known value at once, and
after a restart of the Pi too.

**4. Commands are not retained.**
They pass once and Node-RED, always connected on the same Pi, acts on them.
Nothing can lie around and fire again, so no expiry is needed - and the
panels could not set one anyway.

**5. The preview goes live when a broker answers.**
It connects the way the Deploy dialog does, subscribes to the project's
topics, and shows what arrives. It behaves like the device: a Button's or a
Switch's command is published for real, and the answer comes back from the
broker, not from the mock engine. Without a broker it stays a simulation, as
today, and it can be switched either way.

**6. No value, nothing shown - on the devices and in the preview.**
Until a real value arrives, a panel shows nothing for that topic instead of
the first example; so does the live preview. Examples stay what they are for:
designing in the editor, and the simulation. This changes the firmware of all
three boards and the Android app. The e-paper is retired and keeps its
behaviour.

What "nothing" means per type, agreed the same day - built on the firmware,
the Android app and in the designer, and written into `device-contract.md` §4
"No value until one arrives":

| Type | Without a value |
|---|---|
| MQTT Data Field | nothing, no unit or prefix |
| MQTT Icon Field | no icon |
| Level Indicator | frame visible, no fill, no text |
| Arc Level | track visible, no fill, no marker, no number |
| Switch | frame visible, no segment marked |
| Tab Control | the first panel |
| MQTT Data Line | not drawn |
| Label placeholders | none refer to topics, nothing changes |

How the preview went live, built the same day: entering preview connects
through the Deploy dialog's broker setting (`useMqttConnection`) and
subscribes to every project topic and binding. While connecting it already
counts as live and shows no values, rather than flashing the examples first.
Live, the Topic Values fields show what arrived and are read-only, and a tap
is published without the mock engine; a Live / Simulation switch sits in the
panel's header, and no broker falls back to the simulation with a line
saying so. `e2e/live-preview.spec.ts` covers it against the local broker.

## Order of work

1. **Bridge**: the flow built from one module whose logic is tested in e2e,
   the installer (backup, add or update the tab, uninstall) in
   `pekaway-install.sh`, and a HIL check against the Pi when it is reachable.
2. **Empty until real** (decision 6): firmware and Android start every topic
   empty, and every renderer draws an empty value the same way on the device
   and in the designer - defined per object type, with conformance covering
   the empty case.
3. **Live preview** (decision 5): connection, subscriptions, real publishes,
   the live/simulation switch, and e2e specs against the local broker.
4. **Contract**: `screenbee/state` and `screenbee/cmnd` in
   `device-contract.md`, the reserved client ids, and the empty-value rule.
