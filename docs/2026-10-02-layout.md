# Layout containers in the designer

Agreed 2026-10-02, from an interview with the user (agent-skills
`interview-me`, then `spec-driven-development`); approved by the user the
same day.

## Capability map

| Module | What | Where | Depends on |
|---|---|---|---|
| `layout-model` | Container object types, the layout computation (measure and arrange, shared grid columns), a master's content area, round screens, migration of existing screens, dissolving containers at deploy | designer (`lib/`), one DDF field | - |
| `layout-canvas` | Working with containers on the canvas and in the object tree: dropping into a container at an insertion line, moving between containers, container properties | designer (UI) | `layout-model` |
| `layout-blocks` | Building blocks placed into containers; a block in a grid spreads over the grid's columns | designer (`lib/bausteine.ts`, block dialog) | `layout-model` |
| `layout-templates` | A screen's «Layout» option: copy templates for the screen's root container, and changing it without losing content | designer (UI) | `layout-canvas` |

Build order: `layout-model` → `layout-canvas`, `layout-blocks` → `layout-templates`.

## Objective

A screen is built today by placing every object with its own x, y, width
and height. That position is held, not derived, so every change that moves
sizes costs a round of moving things by hand:

- a size step (S/M/L, docs/2026-09-30-size-scale.md) makes a control taller
  and everything under it has to be pushed down;
- another device or resolution means placing every object again;
- placing exactly - two blocks' controls on one edge, labels lined up - is
  tedious, and each block brings its own label width, so their controls
  never line up anyway.

From here on **positions follow from a structure.** A screen is divided into
containers - a vertical stack, a horizontal stack, a grid, or a free area
where objects are placed as today - and an object put into a container gets
its place and its size from it. A screen survives a change of size step or
device without work by hand, blocks one under another line up by
themselves, and a control is dropped into a container instead of drawn as a
rectangle.

This is the designer's business only. At deploy the designer computes every
position into the x, y, width and height devices get today; firmware and the
Android app are unchanged.

It is also the structure a later piece of work builds on: the VanPi bridge
is to offer a layout for its own entities, embedded in its announcement, as
a subset of these containers (to be specified separately).

Decided with the user 2026-10-02:

- Four containers: `vertical-stack`, `horizontal-stack` and `grid`, named
  after Home Assistant's dashboard cards, and `free`, cartesian as today.
  The Switcher stays as it is (Home Assistant's `conditional`).
- **Width from the container, height from the size step.** A control takes
  the width its container gives it and the height of its size step; text
  the height of its font. Only in `free` does an object have its own width
  and height.
- **Shared grid columns.** A group in a grid does not have columns of its
  own: its pieces take the grid's columns, and a column is as wide as the
  widest of its cells across all groups (CSS calls this a subgrid). Labels
  of all blocks line up, and so do their controls.
- **The master keeps inheriting live,** as today: what lies on it shows on
  every screen using it and cannot be changed there. A master may use
  containers for its own objects (a header as a horizontal stack). Screens
  never put content into a master's containers.
- **A master has a content area,** a rectangle, inherited live: where its
  screens may draw. It is the whole screen by default, and on a round
  screen the largest square that fits in the circle. It can be moved and
  resized - towards the circle's enclosing square for rings, a little
  larger than the inscribed square for a row of buttons with cut corners;
  the pixel-exact preview shows what is cut.
- **A screen's layout is a copy.** A screen chooses which container fills
  the content area, through a «Layout» option as in PowerPoint; a new
  screen gets a sensible default. Choosing a layout copies its containers
  into the screen, where they are the screen's to change. Changing the
  layout of a screen with content moves the content of containers that go
  into the container that stays, appended in order - nothing is lost
  silently, and undo is there too.
- **A screen is its own root container** (decided 2026-10-02, over
  wrapping its objects into a container object): `screen.layout` says which
  container it is (`free`, a stack, a grid) and its properties; the
  screen's objects are the root's children. Every screen has one from the
  start - a screen from before containers loads as `free`, its objects
  exactly where they were - and canvas, object tree and the master's
  objects drawn among the screen's keep working on the screen's objects as
  today.
- **A round screen is said by the device description:** a new DDF field
  `screen.shape` (`"rect"` by default, `"round"` for the Knob).
- **Editing:** an object is dragged into a container, where a line shows
  where it lands; it is moved within or between containers by dragging on
  the canvas or in the object tree. Drawing a rectangle stays for `free`.
  Spacing and alignment are set on the container, not on each object.

Not part of this:

- the VanPi bridge's layout in its announcement (its own spec, after this);
- layouts that stay linked to their template;
- a conversion that guesses stacks and grids from absolute positions;
- round layouts (objects arranged on a circle);
- sliders with a list of values (#33), units on sliders and dials;
- any change to firmware or the Android app.

  (`lib/object-order.ts:105`); at export their objects are inlined into

## Behaviour

### Containers and the layout computation (`layout-model`)

**Types.** Four new object types with `children`:

| Type | Children placed | Properties |
|---|---|---|
| `vertical-stack` | one under another, each the stack's inner width | `padding`, `gap`, `align` (horizontal: stretch, start, centre, end) |
| `horizontal-stack` | side by side, each its own width and height (a switch keeps its size step), aligned across the stack; the stack as tall as the tallest | `padding`, `gap`, `align` (vertical: start, centre, end), `distribute` (start, centre, end, space-between, fill: each the same share) |
| `grid` | row by row, into its columns | `padding`, `gap`, `columns`: a list, each `auto` (as wide as its widest cell) or a weight sharing what is left |
| `free` | at their own x, y, width, height, as today | `padding` |

`padding` and `gap` default to values from the size scale, so they grow
with the device's pixel density as the controls do.

**Sizes.** The layout computation measures from the leaves up and arranges
from the root down:

- *Measure* - each object says how big it would like to be: a control the
  height of its size step and its minimum width (`controlMinWidth`); a text
  the height of its font and the width of its words; an icon its step's
  square; a bar or slider the height its track needs; a ring (gauge, dial)
  as wide as it is offered, its diameter snapped to the size scale's grid
  (`snapDiameter`); a switcher the tallest of its panels' contents; a
  `free` container the height it was given (in a stack: the stack's width,
  its own height - decided 2026-10-02, no fixed aspect ratio).
- *Arrange* - each container hands out its inner rectangle and writes the
  resulting x, y, width and height into its children, relative to itself as
  every child's coordinates already are.

The result is written into the objects after every change, as
`normalizeGroups` does for groups. Everything that reads positions today -
the canvas, the preview, thumbnails, baked bitmaps, deploy - keeps reading
finished coordinates and does not change. Inside a container other than
`free`, an object's x, y and width are outputs; editing them is not offered.

**Shared grid columns.** A `group` directly in a `grid` lays its pieces into
consecutive columns of that grid, left to right, and they take part in
measuring those columns: a column is as wide as the widest cell in it,
whichever group the cell belongs to. A group wider than the grid's columns
starts a new row. Elsewhere a group is what it is today.

**Too little room.** Content taller than its container is drawn as it falls
and cut where the screen ends, as on the device; the designer marks the
container (a warning on it and in its properties), it does not shrink
anything to fit.

**Switcher.** In a container a switcher takes the width it is given and the
height of its tallest panel. Each panel holds one container (a
`vertical-stack` by default), so a panel's content is laid out too.

**Master and content area.** A master screen has a `contentArea` rectangle
(x, y, width, height). Every screen using the master lays its root
container out in that rectangle; the master's own objects are laid out in
the whole screen. Default: the whole screen; on a round screen the largest
square that fits in the circle (side = diameter / √2, centred). It is
edited on the master, and a screen follows it live.

**Round screens.** The DDF's `screen` block gets `shape`: `"rect"` (the
default when absent) or `"round"`. The Knob's DDF says `"round"`.

**Existing projects.** On load, a screen without `layout` gets
`{ type: "free" }`; its objects stay exactly where they were. Idempotent,
in `migrateProject`; a project looks and deploys exactly as before (the
device export never reads `layout`).

**Deploy.** Containers are dissolved like groups: their children become
absolute objects within the screen or within the switcher panel they lie
in. Devices get what they get today; switchers and panels keep their
hierarchy.

### Working with containers (`layout-canvas`)

- A «Layout» section in the toolbar: `Vertical Stack`, `Horizontal Stack`,
  `Grid`, `Free`.
- Placing an object or a container into any container but `free` is a
  click or a drag to a spot in it: a line shows where it lands - between
  two objects of a stack, into a cell of a grid. Its size follows from the
  container. In `free`, a rectangle is drawn as today.
- An object is moved within its container, or into another one, by
  dragging it on the canvas - the same insertion line - or in the object
  tree, which shows the containers.
- Selecting a container shows its properties: padding, gap, alignment,
  distribution, columns. Selecting an object in it shows its own
  properties, with x, y and width read-only where the container sets them;
  its size step stays editable.
- A master shows its content area as a frame that is moved and resized
  like an object; screens show it, not editable.

### Blocks in containers (`layout-blocks`)

- A block (docs/2026-09-30-block-discovery.md) is placed into a container
  as everything else: Insert in the block dialog, then a click at the
  insertion line; in `free` as today, by drawing its rectangle.
- A block arrives as a group, as today. In a `grid`, its name falls into
  the first column and its control into the next, so the blocks of a grid
  line up. An entry with several parts: its name, then each part, each a
  row of its own across the grid's columns.
- The block builders no longer decide a label's width or a control's
  position inside a container; they decide what the pieces are and how
  each is sized by its step. In `free` a block is laid out as today.

### A screen's layout (`layout-templates`)

- A screen has a «Layout» option. Choosing one replaces the screen's root
  container by a copy of the template's containers; the content of
  containers that are not in the new layout is appended to the container
  that stays (the first one, in order). One undo step.
- Templates, built in: «One column» (`vertical-stack`), «Name and control»
  (`grid` with columns `auto`, 1), «Two columns» (a `horizontal-stack` of
  two `vertical-stack`s), «Free» (`free`).
- A new screen gets «Name and control».
- A template is a copy: changing a screen's containers afterwards does not
  touch the template, nor the other way round.

## Code style

As in the code around it: plain functions over the object tree, no
classes, comments that say why. The layout computation is pure - objects
in, objects out - like `normalizeGroups`:

```ts
/**
 * Every container's children placed and sized (docs/2026-10-02-layout.md):
 * measured from the leaves up, arranged from the root down. Objects outside
 * a container, and those in `free`, keep their own geometry.
 */
export function layoutObjects(objects: ScreenObject[], area: Rect, scale: LayoutScale): ScreenObject[]
```

## Testing strategy

- `e2e/layout-model.spec.ts` (Node, no browser): each container's
  arrangement; size steps and fonts as heights; shared grid columns across
  groups; a switcher's height; the content area on a round and a square
  screen; migration leaves an old project's geometry and its deploy zip
  unchanged; deploy dissolves containers and keeps switchers.
- `e2e/layout-canvas.spec.ts`: dropping at the insertion line, moving
  between containers on the canvas and in the tree, container properties,
  read-only geometry, the master's content area.
- `e2e/bausteine.spec.ts`: blocks in a grid line up; blocks in `free` as
  today.
- `e2e/layout-templates.spec.ts`: choosing a layout, content moving into the
  container that stays, undo, a new screen's default.
- A device check at the end: a screen built with containers on the 4.3B and
  the Knob, against the preview (added to the relevant HIL fixture).

## Boundaries

- **Always:** devices get what they get today; an existing project looks
  and deploys as before; the handbook updated in the same piece of work;
  typecheck and the affected specs green before each commit.
- **Ask first:** the DDF field in `schaltli-firmware`; whether new object
  types in the editable project need a `systemGeneration` step; anything
  that changes what the deploy zip contains.
- **Never:** change firmware rendering or the device contract for this;
  guess containers from absolute positions.

## Success criteria

- [ ] Changing a screen's controls from M to L, or the project to another
      device, leaves a screen built with containers without overlaps and
      without work by hand.
- [ ] Three blocks in a «Name and control» grid have their names and their
      controls on one edge each.
- [ ] A control is put into a stack or grid by a click at the insertion
      line, without drawing a rectangle.
- [ ] A project from before this loads, looks and deploys exactly as before.
- [ ] On the Knob the content area is the inscribed square by default and
      can be resized; the preview shows what is cut.
- [ ] Changing a screen from two columns to one keeps all its content.
