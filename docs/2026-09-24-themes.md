# Capability map: colour themes

Status: proposed 2026-09-24. Decisions in this file were taken with the
user on 2026-09-24; the module specs live next to it, named by module id.

## Why

On a colour display the designer offers 140 named colours per property and
leaves it to the user to make a screen look coherent, and every screen looks
like every other. Themes take that freedom away and give something better
in return: a small set of curated palettes, each with a light and a dark
variant, chosen per screen, and switched on the device at runtime - by hand
now, by time of day later.

## Decisions taken (apply to every module)

| Question | Decision |
|---|---|
| Where the switch comes from | One retained MQTT topic for all devices, `schaltli/state/theme` = `light` \| `dark`, set through `schaltli/cmnd/theme`. Anything may set it: a Switch on a screen, Pekaway, later Node-RED at 22:00. No clock on the ESP32 is needed. |
| Grey and 1-bit devices | Get one variant (the theme's light one, quantised as today). The topic changes nothing on them: e-paper has no light to save and re-drawing costs. Only Knob, 4.3B and Android switch. |
| Where a screen's theme comes from | Its own, else its master's. Every screen has a master; there is no project theme (user, 2026-09-25). |
| Where themes come from | A fixed set shipped with the designer, about 6-8, not editable. One of them reproduces today's creation palette exactly, so a migrated project usually looks the same. |
| Hex values | Gone. A colour property holds a role name (or `transparent`), never a hex. There is no productive data yet ("tabula rasa", user 2026-09-24), so nothing is kept for compatibility: no cached hex beside the role, no second representation. |
| Existing project files | The few that exist (test fixtures, the generation corpus) open through a one-pass migration on load that replaces each hex by the nearest role of the theme `lavender`; the file is written back on save. Nothing else is done for old files. |
| Screen backgrounds | A theme's `surface` is a flat colour in the first version. The model leaves room for an optional background image per variant later (`surface` as colour *or* image); a texture costs a bitmap per device resolution and variant on the device, so it is not in `theme-model`. |
| Contract | Open - decided at the start of `theme-export`. Either the exporter resolves roles to hex for the device, light now and dark beside it later (export format unchanged, deploy keeps working throughout), or the export carries roles and the theme table and the device resolves (generation 2.0, deploy only once firmware and app read it). |

## Modules

| Module id | Responsibility | Depends on | Repo |
|---|---|---|---|
| `theme-model` | Shipped themes and their roles; a project's screens choose a theme; objects bind roles instead of hex; one resolution API used by every renderer, thumbnail and preview; the colour picker becomes a role chooser; light/dark preview toggle in the editor; migration of literal colours on load; handbook | - | this |
| `theme-export` | Both variants reach the device, in whichever of the two contract shapes is chosen; bitmaps that bake colours are produced per variant; `docs/device-contract.md` describes it; the HIL reference render can draw the dark variant | `theme-model` | this |
| `theme-topic` | The topics in the contract and the handbook's MQTT pages; the bridge turns `cmnd/theme` into a retained `state/theme`; a "Theme" block that puts a light/dark switch on a screen | - | this |
| `device-switch` | The three firmwares and the Android app subscribe to `schaltli/state/theme` and draw the matching variant; e-paper firmware ignores it. Time-of-day scheduling later is a Node-RED flow publishing the topic, no device work | `theme-export`, `theme-topic` | firmware repo, schaltli-android |

Build order: `theme-model` → `theme-export` → `theme-topic` → `device-switch`.

`theme-topic` needs nothing from the others and could go first, but it is
useless until a device listens; it is placed before `device-switch` so the
contract is written when that work starts. `device-switch` cannot be built
from this repository; this map only fixes what it has to read.

## Interfaces at the boundaries

- `theme-model` → `theme-export`: `resolveRole(theme, role, variant, depth)`, `themeFor(project, screen)` and the list of roles; the exporter either asks for `"light"` and `"dark"` for every colour it writes or bakes, or writes the roles and the theme table through.
- `theme-export` → `device-switch`: the export fields for the dark variant, in whichever shape is chosen (spelled out in `theme-export`'s spec and in `docs/device-contract.md`).
- `theme-topic` → `device-switch`: the two topics and their payloads.
